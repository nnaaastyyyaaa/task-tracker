**Тестування застосунку**

Задача: покрити тестами критичну логіку task-tracker (права доступу, переходи статусів, цілісність даних) на рівнях unit / інтеграційні / E2E і довести якість тестів мутаційним тестуванням, а не лише відсотком покриття.

- **Unit-тести** мають бути ізольовані: без БД і мережі, залежності ,репозиторії замінені моками. Вони мають покривати всі важливі сценарії та гілки критичної логіки:
  - неавторизований користувач (відсутня, невідома або прострочена сесія) отримує `401`, йому доступні лише `login` і `register`;
  - `team_member` не може створити проєкт (`403`); не-власник проєкту не може додавати учасників, створювати, редагувати, видаляти задачу та змінювати виконавця (`403`);
  - `owner` може створити проєкт, створити задачу, відредагувати її, призначити виконавця та змінити виконавця;
  - порядок перевірок завжди `401` → `404` → `403` → `400` → `409/422`: неіснуючий проєкт дає `404`, невалідне тіло від чужого користувача не приймається (`403`);
  - переходи між статусами дозволені лише між сусідніми: `todo ⇔ in_progress ⇔ review ⇔ done`; перевіряються всі 16 пар, несусідній перехід дає `422`, той самий статус дає `200` без запису;
  - змінити статус може лише `owner` або виконавець цієї задачі, інший учасник проєкту отримує `403`;
  - виконавець задачі має бути учасником відповідного проєкту, інакше `422` (і при створенні, і при зміні виконавця);
  - валідація: межі довжини `title` / `description` / `name`, `trim`, значення за замовчуванням (`priority = medium`, `description = ""`), невідоме поле в тілі дає `400`, `assigneeId` не ціле число дає `400`, порожнє тіло в `PATCH` дає `400`;
  - реєстрація: email нормалізується (регістр, пробіли), дубль дає `409`, пароль 8–72 байти, хеш пароля не повертається;
  - вхід: однакова `401` для неправильного email і пароля, нова сесія замінює стару, прострочена сесія видаляється;
  - фільтр дошки: без параметра всі задачі проєкту, з `assignee=me` лише задачі поточного користувача, інше значення дає `400`;
  - допоміжна логіка: `parseId` (`0`, `-1`, `1.5`, `abc`, `2147483647`, `2147483648`), `checkBody`, `str`, `checkId`, `isTransient`, `withRetry` (ретраї 100/200/400 мс, постійна помилка не повторюється, після вичерпання спроб `503` + `Retry-After: 5`), мапінг помилок в `errorHandler` (`AppError`, transient, validation, невідома помилка дає `500` без витоку деталей, невідомий маршрут дає `404`);
  - модуль `task` має бути покритий тестами на 100%.

- **Інтеграційні тести** працюють із реальними залежностями: PostgreSQL і реальним HTTP-сервером Fastify (`fastify.inject`); кожен тест ізольований, БД очищується між тестами. Вони перевіряють те, що неможливо перевірити моками:
  - маршрут → контролер → сервіс → репозиторій → БД для кожного ендпоінта, коректні коди та формат відповіді `{ data }` / `{ error: { code, message } }`;
  - cookie `sid` (`httpOnly`, `sameSite`, `maxAge`), життєвий цикл сесії в БД: створення, прострочення, видалення після `logout`;
  - складений зовнішній ключ `(project_id, assignee_id) → ProjectMember` на рівні БД: `P2003` перетворюється на `422`;
  - унікальність email та пари (проєкт, учасник): `P2002` дає `409`; `CHECK`-обмеження на довжину (`P2004` наразі не мапиться, тест фіксує поточну поведінку);
  - конкурентна зміна статусу: два паралельні запити, один отримує `409`;
  - `updated_at` змінюється при кожній зміні задачі, порядок задач за `created_at, id`;
  - видалення задачі: `204`, повторне видалення дає `404`; видалення проєкту каскадно видаляє задачі та членства;
  - недоступність БД дає `503` для читання; створення (`create`) не повторюється.

- **E2E-тести** 
  - реєстрація `team_lead` і `team_member` → вхід → створення проєкту → додавання учасника за email → створення задачі й призначення виконавця → виконавець переводить задачу `todo → in_progress → review → done` → дошка з фільтром «усі» / «лише мої» → видалення задачі → вихід;
  - негативний наскрізний сценарій: `member` намагається створити проєкт, змінити виконавця, видалити чужу задачу; сторонній користувач не бачить проєкт; після `logout` старий `sid` більше не працює;
  - сценарій «владний» для багатьох користувачів: два проєкти з різними власниками не бачать задач одне одного.

- **Мутаційне тестування** (Stryker + `vitest-runner`) на критичних модулях `task`, `project`, `user`, `utils`:
  - поріг mutation score фіксується в конфігурації (`thresholds.break`), звіт зберігається в репозиторії;
  - кожен вижилий мутант класифікується як «реальна прогалина», «еквівалентний» або «прийнятний» з обґрунтуванням в один рядок;
  - для кожної реальної прогалини додається або підсилюється тест (асерти на значення, побічні ефекти в БД, а не лише на статус `200`);
  - прогін відтворюється командою `npm run test:mutation`.

- **Аудит «зелених» тестів**: топ-3 випадки, де всі тести проходили, але реальний баг лишався непоміченим (наприклад, мутант у `Math.abs(...) === 1`, у `&&` / `||` перевірки прав на статус або в межі `expires_at <= now`); для кожного вказано коміт із підсиленням тесту та зміну критерію в `spec.md`.

- **Відтворюваність і чистота**: усі види тестів запускаються окремими скриптами (`test:unit`, `test:int`, `test:e2e`, `test:cov`, `test:mutation`) на чистому клоні; тести не залежать від порядку виконання, нестабільних (flaky) тестів немає; в репозиторії відсутні `coverage/`, `.stryker-tmp/`, `node_modules/`.


**Критерії гарного артефакту**:
1. `npm run test:cov`: покриття **гілок** ≥ 85% у `src/modules/{project,user,projectMember}` і `src/utils`; для `src/modules/task` 100%.
2. `npm run test:mutation`: mutation score ≥ 80% на цих же файлах; поріг записаний у `stryker.config.json` як `thresholds.break`.
3. Усі вижилі мутанти класифіковані в `docs/mutation/survivors.md` (реальна прогалина / еквівалентний / прийнятний + причина одним рядком);
   для кожної реальної прогалини є новий або підсилений тест.
4. `npm run test:unit`, `test:int`, `test:e2e` проходять на чистому клоні, двічі поспіль і з `--sequence.shuffle`; нестабільних тестів немає.
