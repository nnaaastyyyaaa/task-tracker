# Аудит spec.md

## 1. Відповідність структури формату

Структура `spec.md` загалом відповідає формату: усі п'ять розділів на місці, у правильному порядку, з потрібним наповненням. Опис містить призначення, права ролей і межі; компоненти мають таблицю та поля «відповідає за», «володіє даними», «залежить від»; розділ взаємодії має реєстр викликів і таблицю API з ролями, тілами та кодами помилок; ER-розділ має діаграму, таблиці полів і переходи статусів; усі шість обов'язкових сценаріїв описано за шаблоном. Ідентифікатори `C-`, `E-`, `U-` витримано, діаграми лежать як PlantUML-код у `/docs`.

Відмінності від format-spec: 
- Діаграма компонентів стоїть у розділі 2, тоді як формат вимагає діаграму всіх компонентів у розділі 3.
- У форматі для ER-діаграми досі вказано Mermaid, хоча загальні вимоги кажуть про PlantUML.

## 2. Топ-3 зайві або неправильні залежності

**1. Цикл C-03 ↔ C-04 (неправильна).** Проєкт залежить від Команди (склад учасників для списку проєктів), а Команда від Проєкту (власник для додавання учасника). Через це правило «власник або учасник» розмазане по трьох модулях. Виправлення: зберігати власника в E-03 з полем ролі, тоді залежність C-04 → C-03 зникне.

**2. C-01 → C-02 без контракту (зайва).** Фронтенд «залежить» від модуля користувача, але в таблиці API немає жодного його ендпоінта: ні реєстрації, ні входу. Або додати такі ендпоінти, або прибрати залежність.

**3. Автентифікація не відображена в залежностях (неповна).** Розділ 5 каже, що кожен запит проходить автентифікацію в C-02, але C-03 і C-04 у «Залежить від» його для цього не мають, а «поточний користувач» у реєстрі передається лише в C-05. Або додати C-02 до залежностей усіх модулів, або описати автентифікацію як наскрізний крок перед ними.
