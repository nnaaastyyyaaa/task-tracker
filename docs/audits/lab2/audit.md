# Аудит: прототип → БД

## 1. Топ-3 зрізані кути, знайдені й виправлені

### 1.1. Тіло запиту перекривало довірені аргументи

- **Було.** `service.create({ user: request.user, ...request.body })`. Ключі з тіла перекривають довірені, бо йдуть після них. Клієнт міг передати `{"user": {"id": 1, "role": "team_lead"}}` і діяти від чужого імені. У задачах так само підмінялися `projectId` і `taskId` з URL.
- **Стало.** Контролер передає тіло окремим аргументом: `taskService.create(request.user, parseId(request.params.projectId), request.body)`. Сервіс спершу перевіряє права, потім `checkBody(body, [...])` відкидає невідомі ключі з `400`.

### 1.2. База даних не гарантувала того, що обіцяє spec

- **Було.** `Task.assignee_id` міг бути `NULL`, FK вів на `User`, а не на учасника проєкту. Назва задачі могла бути порожньою. Перевірка «виконавець є учасником» жила лише в коді сервісу.
- **Стало.** Міграція додає складений FK `(project_id, assignee_id) → ProjectMember (project_id, user_id)`, `NOT NULL` на `assignee_id`, обмеження довжини й CHECK-и на непорожні `name` і `title`. Перед зміною схеми міграція виправляє старі дані: задача без валідного виконавця переходить до власника проєкту, а власники без запису в `ProjectMember` отримують його. Порушення FK перетворюється на `422 ASSIGNEE_NOT_MEMBER` (`P2003`).

### 1.3. Порядок перевірок і права за глобальною роллю

- **Було.** `create` і `update` задач спершу перевіряли глобальну роль `team_lead`, а вже потім шукали ресурс. Неіснуючий проєкт давав `403` замість `404`. `changeAssignee` валідував тіло до перевірки `404/403`. `addMember` не перевіряв існування проєкту.
- **Стало.** Єдиний шлях: `#projectRole` або `#taskWithRole` (ресурс → `404`), `#ownerTask` (права → `403`), потім `checkBody` (→ `400`), потім бізнес-правила (`409`, `422`). Глобальну роль замінила перевірка «власник проєкту».


## 2. Крайові випадки

### 2.1
- **Було.** `GET /projects/{id}/tasks` без фільтра повертає лише задачі поточного користувача. Присвоєння `assigneeId = user.id` стоїть поза `if`. Власник бачить на дошці тільки свої задачі, а spec (R-03) вимагає всіх.
- **Стало.** Додано умову `if (assignee === 'me') assigneeId = user.id;`

### 2.2 
- **Було.** `assigneeId` у `create` не проходить перевірку типу. Для відсутнього чи рядкового значення код іде в `isMember`. У прогоні зі заглушкою це `422`, а в реальній Prisma, ймовірно, помилка валідації клієнта → `500`. Spec вимагає `400`. `checkId` імпортовано, але в `create` не викликається.
- **Стало.** Додано `const assigneeId = checkId(body.assigneeId, 'assigneeId')` перед `isMember`

### 2.3
- **Було.** Редагування задачі приймає `title` з 1 символа (`min: 1`), а створення вимагає ≥2 і CHECK у БД теж ≥2. Прогін: `title: 'a'` пройшов сервіс. У реальній БД CHECK відхилить, а помилка не мапиться, тож буде `500`. 
- **Стало.** Виправлено `min: 2`

### 2.4
- **Було.** Прострочені сесії не видаляються, хоча spec обіцяє періодичне очищення. Видаляється лише та, що перевіряється.
- **Стало.** Додано `setInterval` у `server.js` з `deleteMany({ where: { expires_at: { lt: now } } })`

## 3. Коректність запитів

**N+1 немає.** Жоден запит до БД не стоїть у циклі. Імена виконавців для списку задач отримуються одним `findMany ... in` (`UserRepository.findByIds`) і зіставляються через `Map`. Сесія й користувач читаються одним `include`.

Кількість звернень не залежить від кількості задач чи учасників, тобто твердження зі spec «фіксована» правильне. 

| Сценарій | Звернень у коді | Із чого складається |
| --- | --- | --- | --- |
| A-02 вхід | 3–4 | пошук email, пошук попередньої сесії, видалення, створення | 
| R-01 список проєктів | 2 | id проєктів користувача, проєкти за id | 
| R-02 проєкт | 3 | проєкт, роль, список учасників | 
| R-03 дошка | 3–4 | проєкт, роль, задачі, імена (пропускається, якщо задач немає) | 
| R-04 задача | 4 | задача, проєкт, роль, імена |
| U-02 додавання учасника | 5 | проєкт, роль, користувач за email, вставка, список |
| U-03 створення задачі | 5 | проєкт, роль, членство, вставка, імена | 1 |
| U-04 зміна статусу | 6 (3, якщо той самий) | задача, проєкт, роль, `updateMany`, перечитування, імена |
| U-05 зміна виконавця | 6 | задача, проєкт, роль, членство, оновлення, імена | 
| U-06 видалення | 4 | задача, проєкт, роль, видалення | 
| U-07 редагування | 5 | задача, проєкт, роль, оновлення, імена |

## 4. Поведінка на збоях

| Ситуація | За spec | У коді |
| --- | --- | --- |
| Тимчасовий збій (`P1001`, `ECONNREFUSED` тощо) на читанні | ретраї 100/200/400 мс → `503` + `Retry-After: 5` | збігається: 1 спроба + 3 повтори, сумарно ≈700 мс, далі `AppError 503 STORAGE_UNAVAILABLE` із заголовком `Retry-After: 5` |
| Збій минув після двох невдач | успіх | успіх з третьої спроби |
| Постійна помилка (`P2002`) | без повторів | 1 спроба, помилка прокидається |
| Код з `cause.code` (обгортка драйвера) | розпізнається як тимчасовий | розпізнається |
| Створення (A-01, U-01, U-03) | не повторюється → `503` | репозиторії викликають `create` без `withRetry`, а `errorHandler` відповідає `503` |
| Дубль учасника | `409 ALREADY_MEMBER` | `P2002` → `false` → `409` | 
| Порушення складеного FK | `422 ASSIGNEE_NOT_MEMBER` | `P2003` → `422` у `create` і `update` | 
| Порушення CHECK у БД (`P2004`) | відповідний код | **не мапиться**, потрапляє у `500` |
| Зупинка БД під час запиту | `503` | не перевірено на живій БД |
