# Аудит «зелених» тестів

## 1. Межа 500 в `errorHandler.js:62`: витік внутрішніх деталей

**Що не ловили тести.** Були лише кейси зі статусом 403 і `Error` без `statusCode`. Три мутанти (`< 500` → `true`, `&&` → `||`, `<` → `<=`) жили.

**Реальний баг.** Помилка зі статусом ≥ 500 повернулася б клієнту з кодом `BAD_REQUEST` і власним `message` замість `INTERNAL_ERROR`. Це витік внутрішніх деталей, а при статусі рівно 500 ще й неправильний код.

**Підсилення.** У `errorHandler.test.js` кейси 500/501/502/599: відповідь 500, `INTERNAL_ERROR`, фіксований текст, помилка залогована, `reply.code` не викликається.

## 2. `errorHandler.js:57`: статус 400 без поля `validation`

**Що не ловили тести.** Єдиний тест на 400 передавав `validation: true`. Мутант `=== 400` → `false` жив.

**Реальний баг.** Зламаний JSON має статус 400, але не має `validation`, тож отримав би `BAD_REQUEST` замість `VALIDATION_ERROR`. Клієнт, що розрізняє коди, зламався б.

## 3. Роль користувача: `user/service.js:38`, `projectMember/service.js:29`

**Що не ловили тести.** Усі перевіряли лише `status: 400`. Мутант `'VALIDATION_ERROR'` → `""` жив у обох модулях.

**Реальний баг.** Помилка валідації ролі з порожнім кодом порушує формат `{ error: { code, message } }`, і клієнт не відрізнить її від інших 400.

**Підсилення.** `it.each(['admin', '', null, регістр])` перевіряє `code`, а також що репозиторій і `bcrypt.hash` не викликалися.

## 4. projectMember/entity.js:18-19: toEntity() без жодного виклику в тестах
