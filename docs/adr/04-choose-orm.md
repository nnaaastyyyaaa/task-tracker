# Доступ до PostgreSQL: Prisma ORM

## Контекст і проблема

Після переходу з прототипу на статичних даних до реальної бази (ADR 03) репозиторії потрібно навчити працювати з PostgreSQL. Дані пов'язані складеними ключами (учасник проєкту, виконавець задачі), а сценарії вимагають транзакцій, оптимістичного оновлення статусу та перетворення порушень обмежень БД на коди помилок spec. Потрібно обрати спосіб доступу до бази: ORM, конструктор запитів чи «сирий» драйвер.

## Чинники рішення

- Кількість звернень до БД на сценарій фіксована, без N+1 (вкладені створення, `include`, вибірка `in`)
- Міграції, які можна відтворити однією командою (`prisma migrate deploy`)
- Підтримка обмежень БД зі spec: складений зовнішній ключ, `NOT NULL`, `CHECK`
- Зрозумілі коди помилок для порушень обмежень (унікальність, зовнішній ключ)

## Розглянуті варіанти

- Prisma ORM (з адаптером `@prisma/adapter-pg`)
- Драйвер `pg` із SQL-запитами вручну

## Результат рішення

Обрано Prisma ORM, тому що вона дає декларативну схему з відтворюваними міграціями, вкладені операції й `include`, які тримають кількість звернень фіксованою, та стабільні коди помилок (`P2002`, `P2003`) для відображення на відповіді spec.

### Наслідки

- Плюс: схема в `prisma/schema.prisma` є єдиним описом моделі, міграції застосовуються командою `npm run db:migrate`.
- Плюс: параметризовані запити виключають SQL-ін'єкції, вкладений `create` створює проєкт і власника в одній транзакції.
- Плюс: порушення унікальності й складеного FK перетворюються на `409` і `422` за кодами `P2002` і `P2003`.
- Мінус: `CHECK`-обмеження не виражаються в `schema.prisma`, тому їх додано вручну в SQL міграції; коди таких порушень (`P2004`) потрібно відображати окремо.

## Плюси і мінуси варіантів

### Prisma ORM

- Плюс: декларативна схема, міграції, вкладені операції, готові коди помилок.
- Плюс: найменше ручного SQL для типових операцій.
- Мінус: `CHECK` і складні обмеження лише через ручний SQL у міграціях.
- Мінус: складніші запити з об'єднаннями доводиться розбивати або писати сирим SQL.

### Драйвер `pg` із SQL вручну

- Плюс: повний контроль, мінімум залежностей, будь-які запити.
- Мінус: найбільше коду, ручні міграції та складання результатів.
- Мінус: вищий ризик помилок і SQL-ін'єкцій при ручному складанні запитів.
