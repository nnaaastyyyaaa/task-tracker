# task-tracker — специфікація

## 1. Опис застосунку

### Призначення

task-tracker — вебзастосунок на Node.js для керування задачами в командах, спрощений аналог Jira. Team lead створює проєкти, додає до них учасників команди та створює й призначає задачі. Учасники команди бачать проєкти, до яких їх додали, і працюють із задачами на канбан-дошці.

### Ролі та права

Роль є властивістю користувача (`E-01`): `TEAM_LEAD` або `TEAM_MEMBER`.

| Дія                                    | Team lead                         | Team member              |
| -------------------------------------- | --------------------------------- | ------------------------ |
| Створити проєкт                        | ✓                                 | ✗                        |
| Додати учасника до проєкту             | ✓ (лише у своєму проєкті)         | ✗                        |
| Переглянути список проєктів            | ✓ (створені ним)                  | ✓ (де його додано)       |
| Переглянути дошку проєкту              | ✓ (свій проєкт)                   | ✓ (де його додано)       |
| Відфільтрувати задачі (усі / лише мої) | ✓                                 | ✓                        |
| Створити задачу й призначити виконавця | ✓ (у своєму проєкті)              | ✗                        |
| Змінити виконавця задачі               | ✓ (у своєму проєкті)              | ✗                        |
| Змінити статус задачі                  | ✓ (будь-яка задача свого проєкту) | ✓ (лише призначена йому) |
| Видалити задачу                        | ✓ (у своєму проєкті)              | ✗                        |

### Межі системи

**У межах:**

- проєкти, учасники проєктів, задачі;
- дошка зі статусами TODO / IN_PROGRESS / REVIEW / DONE;
- фільтр «усі учасники» / «лише мої задачі»;
- обмеження доступу за ролями.
- редагування назви, опису та пріоритету існуючої задачі;
- видалення проєкту та видалення учасника з проєкту;

**Поза межами (перша версія):**

- коментарі, вкладення, сповіщення, спринти, історія змін.

## 2. Компоненти

Застосунок складається з шести компонентів: клієнтської частини, чотирьох предметних модулів серверу (користувач, проєкт, команда, завдання) і бази даних. Кожен предметний модуль відповідає за одну частину предметної області й єдиний змінює свої дані.

| ID   | Назва      | Що це              | Технологія   |
| ---- | ---------- | ------------------ | ------------ |
| C-01 | Фронтенд   | клієнтська частина | TODO: обрати |
| C-02 | Користувач | модуль серверу     | Node.js      |
| C-03 | Проєкт     | модуль серверу     | Node.js      |
| C-04 | Команда    | модуль серверу     | Node.js      |
| C-05 | Завдання   | модуль серверу     | Node.js      |
| C-06 | База даних | сховище даних      | TODO: обрати |

### Діаграма компонентів

[Діаграма](./docs/diagrams/img/component.png)

### C-01. Фронтенд

Веб-інтерфейс, через який працюють обидві ролі.

- **Відповідає за:**
  - головну сторінку зі списком проєктів користувача; кнопка «Створити проєкт» доступна лише team lead;
  - сторінку проєкту: дошку з чотирма стовпцями (TODO / IN_PROGRESS / REVIEW / DONE) і перемикач «Усі учасники» / «Лише мої»;
  - форми створення проєкту, додавання учасника, створення задачі та зміни виконавця;
  - зміну статусу задачі та видалення задачі;
  - відправлення запитів до сервера та показ помилок користувачеві.
- **Володіє даними:** ніякими.
- **Залежить від:** C-02, C-03, C-04, C-05 (через HTTP/JSON).

### C-02. Користувач

Модуль, що знає, хто виконує запит.

- **Відповідає за:**
  - автентифікацію: визначення поточного користувача та його ролі для кожного запиту;
  - облікові записи користувачів (створення, зберігання пароля у вигляді хешу);
  - пошук користувача за ідентифікатором або `email`.
- **Володіє даними:** E-01 (User).
- **Надає іншим модулям:** поточний користувач із роллю; користувач за `email`; ім'я користувача за ідентифікатором.
- **Залежить від:** C-06.

### C-03. Проєкт

Модуль, що відповідає за проєкти як такі.

- **Відповідає за:**
  - створення проєкту (лише роль `TEAM_LEAD`);
  - отримання проєкту та списку проєктів, доступних користувачу: team lead бачить створені ним, team member — ті, до яких його додано;
  - визначення власника проєкту.
- **Володіє даними:** E-02 (Project).
- **Надає іншим модулям:** чи існує проєкт; чи є користувач його власником.
- **Залежить від:** C-04 (склад команди для списку проєктів і перевірки доступу), C-06.

### C-04. Команда

Модуль, що знає, хто бере участь у якому проєкті.

- **Відповідає за:**
  - додавання учасника до проєкту за `email` (лише власник проєкту);
  - список учасників проєкту;
  - перевірку, чи є користувач учасником проєкту;
  - список проєктів, у яких бере участь користувач.
- **Володіє даними:** E-03 (ProjectMember).
- **Надає іншим модулям:** чи є користувач учасником проєкту; проєкти користувача; список учасників проєкту.
- **Залежить від:** C-02 (знайти користувача за `email`), C-03 (власник проєкту), C-06.

### C-05. Завдання

Модуль, що відповідає за задачі та їхній життєвий цикл на дошці.

- **Відповідає за:**
  - створення задачі з призначенням виконавця (лише власник проєкту);
  - зміну виконавця (лише власник проєкту);
  - зміну статусу за схемою допустимих переходів (власник проєкту або виконавець задачі);
  - видалення задачі (лише власник проєкту);
  - список задач проєкту, включно з фільтром «лише мої»;
  - правило, що виконавцем може бути лише учасник проєкту.
- **Володіє даними:** E-04 (Task).
- **Залежить від:** C-02 (ім'я виконавця для показу на дошці), C-03 (власник проєкту), C-04 (чи є виконавець учасником; доступ до перегляду), C-06.

### C-06. База даних

Постійне сховище всіх даних застосунку.

- **Відповідає за:**
  - зберігання сутностей E-01–E-04;
  - цілісність даних: зовнішні ключі та унікальні обмеження (наприклад, унікальність `email` і пари «проєкт + учасник»).
- **Володіє даними:** зберігає всі сутності, але змінює їх лише за запитами відповідного модуля: E-01 — C-02, E-02 — C-03, E-03 — C-04, E-04 — C-05.
- **Залежить від:** нікого.

## 3. Взаємодія компонентів

Кожен запит від C-01 спершу проходить автентифікацію в C-02, а далі потрапляє до модуля, що відповідає за ендпоінт. Модулі викликають один одного напряму (виклик функції в межах одного серверу), а до C-06 звертаються через обране сховище.

### Приклад: створення задачі

[Діаграма](./docs/diagrams/img/sequence.png)

### Реєстр взаємодій

| Від                    | До                     | Спосіб         | Що передається                                                   |
| ---------------------- | ---------------------- | -------------- | ---------------------------------------------------------------- |
| C-01                   | C-02, C-03, C-04, C-05 | HTTP/JSON      | запити користувача; у відповідь — дані або код помилки           |
| C-03                   | C-04                   | виклик функції | проєкти користувача, чи є користувач учасником, список учасників |
| C-04                   | C-03                   | виклик функції | чи існує проєкт, чи є користувач його власником                  |
| C-04                   | C-02                   | виклик функції | користувач за `email`                                            |
| C-05                   | C-02                   | виклик функції | поточний користувач, ім'я виконавця                              |
| C-05                   | C-03                   | виклик функції | чи є користувач власником проєкту                                |
| C-05                   | C-04                   | виклик функції | чи є виконавець учасником проєкту                                |
| C-02, C-03, C-04, C-05 | C-06                   | SQL-запити     | читання та запис власних сутностей                               |

### API

Усі ендпоінти вимагають автентифікованого користувача (спосіб автентифікації — див. розділ 6). Тіла запитів і відповідей — JSON.

| Ендпоінт                                      | Модуль | Хто має доступ                     | Запит                                                                                                | Відповідь                                        | Помилки                                                                         |
| --------------------------------------------- | ------ | ---------------------------------- | ---------------------------------------------------------------------------------------------------- | ------------------------------------------------ | ------------------------------------------------------------------------------- |
| `POST /projects`                              | C-03   | Team lead                          | `name` (1–100), `description` (0–1000, необов'язково)                                                | `201`, проєкт                                    | `400` невалідні дані; `401`; `403` не team lead                                 |
| `GET /projects`                               | C-03   | Team lead, team member             | —                                                                                                    | `200`, проєкти, доступні користувачу             | `401`                                                                           |
| `GET /projects/{projectId}`                   | C-03   | Власник проєкту, учасник проєкту   | —                                                                                                    | `200`, проєкт і список учасників                 | `401`; `403` немає доступу; `404`                                               |
| `POST /projects/{projectId}/members`          | C-04   | Власник проєкту                    | `email` користувача                                                                                  | `201`, оновлений список учасників                | `400`; `401`; `403`; `404` проєкт або користувач не знайдені; `409` уже учасник |
| `GET /projects/{projectId}/tasks?assignee=me` | C-05   | Власник проєкту, учасник проєкту   | параметр `assignee=me` необов'язковий: лише мої задачі                                               | `200`, задачі проєкту                            | `401`; `403`; `404`                                                             |
| `POST /projects/{projectId}/tasks`            | C-05   | Власник проєкту                    | `title` (1–200), `description` (0–5000), `assigneeId`, `priority` (LOW / MEDIUM / HIGH)              | `201`, задача зі статусом TODO                   | `400`; `401`; `403`; `404`; `422` виконавець не є учасником проєкту             |
| `GET /tasks/{taskId}`                         | C-05   | Власник проєкту, учасник проєкту   | —                                                                                                    | `200`, задача з усіма полями та іменем виконавця | `401`; `403`; `404`                                                             |
| `PATCH /tasks/{taskId}`                       | C-05   | Власник проєкту                    | `title` (1–200), `description` (0–5000), `priority` (LOW / MEDIUM / HIGH); потрібне хоча б одне поле | `200`, оновлена задача                           | `400` невалідні дані або жодного поля; `401`; `403`; `404`                      |
| `PATCH /tasks/{taskId}/status`                | C-05   | Власник проєкту; виконавець задачі | `status`                                                                                             | `200`, задача                                    | `400`; `401`; `403`; `404`; `422` недозволений перехід статусу                  |
| `PATCH /tasks/{taskId}/assignee`              | C-05   | Власник проєкту                    | `assigneeId`                                                                                         | `200`, задача                                    | `400`; `401`; `403`; `404`; `422` виконавець не є учасником проєкту             |
| `DELETE /tasks/{taskId}`                      | C-05   | Власник проєкту                    | —                                                                                                    | `204`                                            | `401`; `403`; `404`                                                             |     |

## 4. ER-діаграма

[Діаграма](./docs/diagrams/img/er.png)

### E-01. User (C-02)

| Поле          | Тип    | Обмеження                                                |
| ------------- | ------ | -------------------------------------------------------- |
| id            | uuid   | PK                                                       |
| name          | string | 1–100 символів, обов'язкове                              |
| email         | string | унікальне, обов'язкове                                   |
| password_hash | string | обов'язкове; пароль у відкритому вигляді не зберігається |
| role          | enum   | `TEAM_LEAD` / `TEAM_MEMBER`, обов'язкове                 |

### E-02. Project (C-03)

| Поле        | Тип    | Обмеження                                               |
| ----------- | ------ | ------------------------------------------------------- |
| id          | uuid   | PK                                                      |
| name        | string | 1–100 символів, обов'язкове                             |
| description | string | 0–1000 символів, необов'язкове                          |
| owner_id    | uuid   | FK → E-01, обов'язкове; користувач із роллю `TEAM_LEAD` |

### E-03. ProjectMember (C-04)

| Поле       | Тип  | Обмеження                        |
| ---------- | ---- | -------------------------------- |
| project_id | uuid | FK → E-02, частина складеного PK |
| user_id    | uuid | FK → E-01, частина складеного PK |

Пара (`project_id`, `user_id`) унікальна: користувач не може бути доданий до проєкту двічі.

### E-04. Task (C-05)

| Поле        | Тип      | Обмеження                                                           |
| ----------- | -------- | ------------------------------------------------------------------- |
| id          | uuid     | PK                                                                  |
| project_id  | uuid     | FK → E-02, обов'язкове                                              |
| title       | string   | 1–200 символів, обов'язкове                                         |
| description | string   | 0–5000 символів                                                     |
| assignee_id | uuid     | FK → E-01, обов'язкове; має бути учасником проєкту (запис у E-03)   |
| priority    | enum     | `LOW` / `MEDIUM` / `HIGH`, за замовчуванням `MEDIUM`                |
| status      | enum     | `TODO` / `IN_PROGRESS` / `REVIEW` / `DONE`, за замовчуванням `TODO` |
| created_at  | datetime | встановлюється при створенні                                        |
| updated_at  | datetime | оновлюється при кожній зміні                                        |

## 5. Сценарії оновлення даних

У кожному сценарії запит першим проходить автентифікацію в C-02.

### U-01. Створення проєкту

- **Ініціатор і передумова:** автентифікований користувач із роллю `TEAM_LEAD`.
- **Кроки:** C-01 надсилає `POST /projects`; C-02 визначає користувача та роль; C-03 перевіряє роль і валідує дані; C-03 створює запис у E-02 з `owner_id` = поточний користувач.
- **Зміни даних:** E-02 — додається запис.
- **Помилки:** невалідні дані → `400`; роль не `TEAM_LEAD` → `403`. Дані не змінюються.

### U-02. Додавання учасника до проєкту

- **Ініціатор і передумова:** власник проєкту; користувач із вказаним `email` існує.
- **Кроки:** C-01 надсилає `POST /projects/{projectId}/members`; C-04 через C-03 перевіряє, що ініціатор — власник проєкту; C-04 через C-02 знаходить користувача за `email`; C-04 створює запис у E-03.
- **Зміни даних:** E-03 — додається запис (`project_id`, `user_id`).
- **Помилки:** ініціатор не власник → `403`; проєкт або користувач не знайдені → `404`; користувач уже є учасником → `409`. Дані не змінюються.

### U-03. Створення та призначення задачі

- **Ініціатор і передумова:** власник проєкту; виконавець є учасником проєкту.
- **Кроки:** C-01 надсилає `POST /projects/{projectId}/tasks`; C-05 через C-03 перевіряє, що ініціатор — власник проєкту; C-05 валідує поля; C-05 через C-04 перевіряє, що виконавець є учасником; C-05 створює запис у E-04 зі `status = TODO`.
- **Зміни даних:** E-04 — додається запис.
- **Помилки:** невалідні дані → `400`; ініціатор не власник → `403`; виконавець не є учасником → `422`. Дані не змінюються.

### U-04. Зміна статусу задачі

- **Ініціатор і передумова:** власник проєкту, до якого належить задача, або виконавець цієї задачі.
- **Кроки:** C-01 надсилає `PATCH /tasks/{taskId}/status`; C-05 знаходить задачу; C-05 через C-03 перевіряє, чи ініціатор — власник проєкту/виконавець задачі; C-05 перевіряє допустимість переходу зі схеми розділу 4; C-05 оновлює `status` і `updated_at`.
- **Зміни даних:** E-04 — оновлюються `status` і `updated_at`.
- **Помилки:** немає прав → `403`; задача не знайдена → `404`; недозволений перехід → `422`. Дані не змінюються.

### U-05. Зміна виконавця задачі

- **Ініціатор і передумова:** власник проєкту, до якого належить задача; новий виконавець є учасником проєкту.
- **Кроки:** C-01 надсилає `PATCH /tasks/{taskId}/assignee`; C-05 знаходить задачу; C-05 через C-03 перевіряє, що ініціатор — власник проєкту; C-05 через C-04 перевіряє, що новий виконавець є учасником; C-05 оновлює `assignee_id` і `updated_at`.
- **Зміни даних:** E-04 — оновлюються `assignee_id` і `updated_at`.
- **Помилки:** ініціатор не власник → `403`; задача не знайдена → `404`; новий виконавець не є учасником → `422`. Дані не змінюються.

### U-06. Видалення задачі

- **Ініціатор і передумова:** власник проєкту, до якого належить задача.
- **Кроки:** C-01 надсилає `DELETE /tasks/{taskId}`; C-05 знаходить задачу; C-05 через C-03 перевіряє, що ініціатор — власник проєкту; C-05 видаляє запис у E-04.
- **Зміни даних:** E-04 — запис видаляється.
- **Помилки:** ініціатор не власник → `403`; задача не знайдена → `404`. Дані не змінюються.
